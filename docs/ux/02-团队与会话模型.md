# MX-3：团队与会话模型（IA 结构变更）

> 状态：**设计稿，未进入实现**（2026-09-14）
> 触发：用户评审 MX-2 原型后提出的结构性意见（见 §1）
> 影响：`docs/ux/00-信息架构与屏幕清单.md` 的 S1/S3 定义被本文件覆盖；新增 S0、S2-solo 两屏
> 产出：`docs/ux/mockups/s0-new-session.html`、`s3-teams.html`、`s2-solo.html`（`s3-roles.html` 已删除）
> 纪律：仍是纯文档里程碑，**不改任何 `.tsx`**、不动 git 实现代码（AGENTS.md §4.4）

---

## 1. 用户提出的三条意见

1. **「角色管理」应该是「团队管理」**：用户先建团队，团队里放指定类型的 Agent；不同团队类型 = 不同的 Agent 组合。
2. **「新建分身」这件事应该收进团队管理**——创建一个分身 = 往团队里创建一个 Agent；侧栏一级入口应该改成**「新建会话」**。
3. **会话开工时可指定由哪个团队协作，也可以不指定团队**——不指定时由 Axon 内置引擎直接干。理由：任务复杂度不一样，**不是每个任务都值得配一整支队伍**。

这三条合起来是一次心智模型的换轴，值得单独立档。

---

## 2. 换轴：从「分身是一等公民」到「会话是一等公民」

### 2.1 旧模型（MX-1/MX-2 原型）

```
角色（模板） ──spawn──▶ 分身（实例，挂在一棵全局树上）
                         └─ 会话 = 某个分身的消息流（S2 只是分身的一个视图）
```

问题有三个：

| 问题 | 表现 |
|---|---|
| 没有"任务"这个容器 | 分身树是全局唯一一棵，五个不相干的任务的分身混在同一棵树里（原型 S1 里「数据迁移 #5」和「支付回调改造」毫无关系却并列） |
| 起步成本恒定 | 想干任何事都得先想清楚「派哪个角色」，改个错别字也要走 spawn |
| 复用单位错了 | 用户复用的其实是**一套班子**（主控+架构+实现+测试），而不是单个角色 |

### 2.2 新模型

```
Agent 类型（能力模板，= 现协议的 RoleDefinition）
      │  被引用
      ▼
Agent（团队成员：类型 + 本队覆写 + 名字）
      │  组合 + 编队策略
      ▼
Team（团队 = 可复用的班子模板）
      │  session.create 时实例化
      ▼
Session（会话 = 一等公民 = 任务容器）
      └─ 分身树（团队成员在本次会话里跑起来的实例）
```

四层各自的定义与归属：

| 层 | 是什么 | 存在哪 | 屏幕 |
|---|---|---|---|
| **Agent 类型** | 提示词 + 工具白名单 + 审批档 + ForkMode 默认值。能力模板，跨团队复用 | `~/.axon/roles/*.json`（现状不变） | S3 第三个 tab |
| **Agent** | 团队里的一个具名成员：引用一个类型，可做**只减不增**的覆写（模型、工具子集、审批更严） | `~/.axon/teams/<team>.json` 内嵌 | S3 团队详情的成员列表 |
| **Team** | Agent 的组合 + 编队形状 + 并发闸门 + 团队预算 + 上下文默认 | `~/.axon/teams/*.json` | S3 团队卡片 |
| **Session** | 一次任务：题目 + cwd + 执行方式 + 分身树 + 账本切片 + 用量 | 内存（M5 后落盘） | S0 建、S2 用、S1 总览、S7 恢复 |

**关键不变量（沿用 AGENTS.md §5）**：合成顺序仍然是 **角色 → 权限（父∩子白名单）→ 上下文（ForkMode）**，团队只是在最外面加了一层「谁和谁一起上、树长什么形状」。团队不引入新的提权路径：Agent 的覆写只能减能力，不能突破所引用类型的白名单。

## 3. 三种执行方式（S0 的核心选择）

用户说的「不是每个任务都值得配一支队伍」，落成 S0 的三张模式卡：

| 模式 | 什么时候用 | 会话形态 | 屏 |
|---|---|---|---|
| **内置引擎（默认）** | 改错别字、查协议、跑一次测试——一个人就能收敛的活 | 单执行体，无分身树、不落协作账本、无审批穿透链 | `s2-solo.html` |
| **指定团队** | 跨层改动、需要评审或并行 | 按团队编队实例化整棵分身树 | `s2-session.html` |
| **临时编队** | 这一次的特殊组合 | 从 Agent 库现挑 2~6 个，用完即散，可事后「存为团队」 | 同上 |

### 3.1 默认值就是「不组队」

这是本次换轴最重要的产品判断：**默认不组队**。理由与 ForkMode 默认 `none` 同源——**协作是成本，不是福利**。多一个分身就多一份 token、多一条审批链、多一次账本表态。原型里 S0 的「内置引擎」卡片是唯一带选中态的，团队要用户主动点。

### 3.2 单兵会话的诚实边界

`s2-solo.html` 右侧面板明写：

> 单兵会话没有分身树、没有协作账本、没有穿透链——S4 / S5 对它是空的。这是刻意的：小任务不该付编排的心智税。

界面上**不隐藏这个事实**，也不给单兵会话画一棵只有一个节点的假树。

### 3.3 「叫人」：单兵 → 团队的逃生门

真实情况是任务会长大。`s2-solo.html` 演示了完整的升级流：用户追加了一条让任务跨出单人范围的要求（补依赖梳理 + 补导出测试），引擎给出一张**升级提议卡**：

- 建议的团队（测试双人）与每个成员要干的事；
- 明确「升级不丢上下文」：当前 N 条消息作为 lead 的初始上下文（`fork: all`），其余成员按各自 ForkMode 决定看到多少；
- 三个出口：继续单兵 / 换个团队 / 用建议的团队升级。

侧栏的「当前会话」条也常驻一个 `叫人 →`。

## 6. 待用户拍板的开放问题

原型 S3 右侧「待拍板」面板里列的三条，需要在 M4 设计评审前给出结论：

1. **Agent 是团队私有还是全局共享？** 跨团队能否复用同一个 Agent 实体？
   - 私有：模型简单，改一处不影响别队；代价是同一个人配置要复制多份。
   - 共享：复用性好；代价是「本队覆写」要变成引用关系，改动扩散面大。
   - *倾向*：私有（团队 JSON 内嵌成员），复用交给 Agent 类型这一层。
2. **团队能否嵌套？**（子队作为一个成员）
   - 嵌套能表达大型编队，但会让「父∩子白名单」与并发闸门的语义变复杂。
   - *倾向*：不嵌套，用编队形状（星形/链形/自定义父子）覆盖大部分需求。
3. **「临时编队」结束后默认丢弃还是提示存为团队？**
   - *倾向*：默认丢弃，会话结束时给一次「存为团队」的提示（不弹窗，放在会话尾部卡片里）。

另需确认的两条（原型已按倾向画了，但可推翻）：

4. **团队预算与全局预算的关系**：原型按「团队软/硬线在全局档之内取更严者」画。
5. **临时加入的分身**（S1 里「文档 #4」「数据迁移 #5」带的 `临时加入` 标签）算不算团队成员？原型按「不算，只属于本会话」画。

## 7. 与后续里程碑的接口

- **M4（协作动作与落账）**：G10.1/G10.3 决定账本与审批的作用域字段。若 `LedgerRecord` 不带 sessionId，S4 就无法按会话切片，S1 的「12 笔协作」也是假的。建议 M4 一并把 sessionId 打进账本与 usage。
- **M5（会话恢复）**：新模型下恢复单位天然是 Session，落盘最小集 = 会话元信息（题目/cwd/执行方式/team 引用）+ 分身树 + 各分身消息 + 账本切片。S7 的占位屏可据此细化。
- **MU（UI 实现）**：S0 是应用启动的落地屏。实现顺序建议 **S0 → S2-solo → S2 团队会话 → S1 → S3**：单兵链路最短，能最早跑通一条真实端到端。
