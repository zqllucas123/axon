# MX-3：团队与会话模型（IA 结构变更）

> 状态：**设计稿，未进入实现**（2026-09-14）
> 触发：用户评审 MX-2 原型后提出的结构性意见（见 §1）
> 影响：`docs/ux/00-信息架构与屏幕清单.md` 的 S1/S3 定义被本文件覆盖；新增 S0、S2-solo 两屏
> 产出：`docs/ux/mockups/s0-new-session.html`、`s3-teams.html`、`s2-solo.html`（`s3-roles.html` 已删除）
> 纪律：仍是纯文档里程碑，**不改任何 `.tsx`**、不动 git 实现代码（AGENTS.md §4.4）

## 1. 用户提出的三条意见

1. **「角色管理」应该是「团队管理」**：用户先建团队，团队里放指定类型的 Agent；不同团队类型 = 不同的 Agent 组合。
2. **「新建分身」这件事应该收进团队管理**——创建一个分身 = 往团队里创建一个 Agent；侧栏一级入口应该改成**「新建会话」**。
3. **会话开工时可指定由哪个团队协作，也可以不指定团队**——不指定时由 Axon 内置引擎直接干。理由：任务复杂度不一样，**不是每个任务都值得配一整支队伍**。

这三条合起来是一次心智模型的换轴，值得单独立档。

## 2. 换轴：从「分身是一等公民」到「会话是一等公民」

### 2.1 旧模型（MX-1/MX-2 原型）

```
角色（模板） ──spawn──▶ 分身（实例，挂在一棵全局树上）
                         └─ 会话 = 某个分身的消息流（S2 只是分身的一个视图）
```

问题有三个：

| 问题 | 表现 |
|---|---|
| 没有"任务"这个容器 | 分身树是全局唯一一棵，五个不相干的任务的分身混在同一棵树里（原型 S1 里「数据迁移 #5」和「支付回调改造」毫无关系却并列） |
| 起步成本恒定 | 想干任何事都得先想清楚「派哪个角色」，改个错别字也要走 spawn |
| 复用单位错了 | 用户复用的其实是**一套班子**（主控+架构+实现+测试），而不是单个角色 |

### 2.2 新模型

```
Agent 类型（能力模板，= 现协议的 RoleDefinition）
      │  被引用
      ▼
Agent（团队成员：类型 + 本队覆写 + 名字）
      │  组合 + 编队策略
      ▼
Team（团队 = 可复用的班子模板）
      │  session.create 时实例化
      ▼
Session（会话 = 一等公民 = 任务容器）
      └─ 分身树（团队成员在本次会话里跑起来的实例）
```

四层各自的定义与归属：

| 层 | 是什么 | 存在哪 | 屏幕 |
|---|---|---|---|
| **Agent 类型** | 提示词 + 工具白名单 + 审批档 + ForkMode 默认值。能力模板，跨团队复用 | `~/.axon/roles/*.json`（现状不变） | S3 第三个 tab |
| **Agent** | 团队里的一个具名成员：引用一个类型，可做**只减不增**的覆写（模型、工具子集、审批更严） | `~/.axon/teams/<team>.json` 内嵌 | S3 团队详情的成员列表 |
| **Team** | Agent 的组合 + 编队形状 + 并发闸门 + 团队预算 + 上下文默认 | `~/.axon/teams/*.json` | S3 团队卡片 |
| **Session** | 一次任务：题目 + cwd + 执行方式 + 分身树 + 账本切片 + 用量 | **已落盘**（M5：`~/.axon/sessions/<enc(cwd)>/<id>/` = `session.json` + `agents/*.jsonl` + `ledger.jsonl`） | S0 建、S2 用、S1 总览、S7 恢复 |

**关键不变量（沿用 AGENTS.md §5）**：合成顺序仍然是 **角色 → 权限（父∩子白名单）→ 上下文（ForkMode）**，团队只是在最外面加了一层「谁和谁一起上、树长什么形状」。团队不引入新的提权路径：Agent 的覆写只能减能力，不能突破所引用类型的白名单。

## 3. 三种执行方式（S0 的核心选择）

用户说的「不是每个任务都值得配一支队伍」，落成 S0 的三张模式卡：

| 模式 | 什么时候用 | 会话形态 | 屏 |
|---|---|---|---|
| **内置引擎（默认）** | 改错别字、查协议、跑一次测试——一个人就能收敛的活 | 单执行体，无分身树、不落协作账本、无审批穿透链 | `s2-solo.html` |
| **指定团队** | 跨层改动、需要评审或并行 | 按团队编队实例化整棵分身树 | `s2-session.html` |
| **临时编队** | 这一次的特殊组合 | 从 Agent 库现挑 2~6 个，用完即散，可事后「存为团队」 | 同上 |

### 3.1 默认值就是「不组队」

这是本次换轴最重要的产品判断：**默认不组队**。理由与 ForkMode 默认 `none` 同源——**协作是成本，不是福利**。多一个分身就多一份 token、多一条审批链、多一次账本表态。原型里 S0 的「内置引擎」卡片是唯一带选中态的，团队要用户主动点。

### 3.2 单兵会话的诚实边界

`s2-solo.html` 右侧面板明写：

> 单兵会话没有分身树、没有协作账本、没有穿透链——S4 / S5 对它是空的。这是刻意的：小任务不该付编排的心智税。

界面上**不隐藏这个事实**，也不给单兵会话画一棵只有一个节点的假树。

### 3.3 「叫人」：单兵 → 团队的逃生门

真实情况是任务会长大。`s2-solo.html` 演示了完整的升级流：用户追加了一条让任务跨出单人范围的要求（补依赖梳理 + 补导出测试），引擎给出一张**升级提议卡**：

- 建议的团队（测试双人）与每个成员要干的事；
- 明确「升级不丢上下文」：当前 N 条消息作为 lead 的初始上下文（`fork: all`），其余成员按各自 ForkMode 决定看到多少；
- 三个出口：继续单兵 / 换个团队 / 用建议的团队升级。

侧栏的「当前会话」条也常驻一个 `叫人 →`。

## 3.4 作用域规则：什么进会话，什么留全局

> 触发：用户评审时指出「协作账本应该是会话粒度的」。这条意见暴露了 v0.1 原型的一个自相矛盾：
> S4 顶着一级导航的全局屏名分，内容却全是会话内的（右侧写着「本会话汇总」、过滤器写着「限定子树 /0/1」）。

判断标准就一条：**这个屏的主键是什么。**

| 信息 | 天然主键 | 结论 |
|---|---|---|
| 协作账本 | `sessionId`（协作只发生在同一会话的成员之间，`/0/1/2` 这类路径也只在会话内唯一） | **全部进会话**，不留全局入口 |
| 用量明细（按成员 / 按动作） | `sessionId` | 进会话 |
| 预算档位与总额 | 全局（你今天一共花了多少） | 留全局，但下钻到会话 |
| 收件箱（审批与提问） | 双重：请求属于某会话，但「有人卡住等你」是跨会话的 | 两头都要（见下） |
| 团队 / Agent 类型 | 配置文件 | 全局 |

### 落成三条规则

1. **账本与用量从一级导航撑下来，变成会话内视图**。会话条上新增视图切换：`对话 | 账本 12 | 用量 $1.13`。
   跨会话的账本没有语义——把两个不相干任务的 delegate 摆在同一个列表里，读者第一件事就是把它们分开。
2. **审批不做会话内 tab**。审批是打断式的，必须**就地出现在会话流里**（已有审批卡）；藏到另一个 tab 里等于没有。
   全局 S5 收件箱保留，它的唯一职责是**跨会话聚合**：你在 A 会话里干活时，B 会话有人卡住了。
3. **顶栏 chip 随屏切作用域**。在会话屏：`本会话 $1.13/$1.50 · 待批 2 · 本会话账本 12`；
   在全局屏：`今日 $1.49/$5.00 · 待批 2（全部会话）· 活跃会话 3`。**两套数字永不混用**。

### 右侧面板也要有账本

全幅账本视图解决「回顾」，但干活时不能为了采纳一条 delegate 就离开对话。
所以 S2 右侧检视区新增一个**精简账本面板**（`.led-mini`）：

- 只列与**当前查看成员**相关的条目（需要 `ledger.query` 支持 `sessionId` + `participant` 两个过滤，G7.1）；
- 待表态的条目就地给「采纳 / 驳回」按钮；
- 右上角一个展开图标跳全幅。

这就是用户要的「在运行中的会话里直接看本会话的账本面板」。

## 3.6 左右两栏的职责切分（用户 2026-09-14 拍板）

> 触发：用户评审 v0.2 原型时指出——「左侧边栏不用展示当前会话的状态，
> 这部分信息应该展示在右边栏，并且右边栏的信息会随着会话的切换而切换，是会话粒度的」。

这是 §3.4 「看主键」判断标准在**空间布局**上的续集：v0.2 原型已把账本/用量从全局导航撕下来了，
却把同样是会话粒度的**分身树 + 团队条 + 会话标题**留在了左栏（`shell.js` 旧 `sidebarHTML` 的「当前会话」块）。
同一个错误犯了两次：**把会话内部结构放在了会话之间的导航区**。

### 规则：左 = 会话之间，右 = 会话之内

| 栏 | 粒度 | 内容 | 切会话时 |
|---|---|---|---|
| **左栏** | 跨会话 | 全局导航（6 项）+ 会话列表（进行中 / 最近） | **不变**，只移动高亮行 |
| **右栏** | 会话内 | 本会话成员树 → 当前成员详情 → 本会话账本 → 协作动作参考 | **整体换掉** |

落成三条硬规定：

1. **左栏不得渲染任何会话内部结构**。分身树、团队条、「编队 →」入口全部搬到右栏。
   左栏会话行只给三个字段：状态点 / 会话名 / 右侧 meta（团队名或「单兵」）。不可展开子树——
   否则同一棵树会在两个地方渲染，选中态同步是红线（kalo `chat-store.ts` 的教训：双写状态必然不同步）。
2. **右栏顶部常驻「本会话成员」面板**，四个会话屏（`s2-session` / `s2-solo` / `s2-usage` / `s4-ledger`）全部带它。
   顶部而不是底部：右栏的阅读顺序是「谁在干（树）→ 这个人是谁（信息）→ 大家干了啥（账本）」，一栏读完。
   单兵会话也有这个面板，但只有一行「内置引擎 `/0`」+ 「叫人 →」——让代价差别可见（同 §3.2）。
3. **右栏是会话的函数**：实现时右栏整体由 `sessionId` 驱动重建，不允许跨会话保留局部状态（滚动位置除外）。
   右栏里的「当前成员」选中态属于会话状态（每个会话记住自己上次看的是谁），而非全局状态。

### 代价与已知问题

- 右栏现宽 300px（`--inspector-w`），“成员树 + 成员信息 + 账本”三面板在 6 成员时已需滚动；
  分身数 > 20 的折叠/搜索策略仍未画（记在 01 §6）。
- 跨会话直达某个成员（比如从 S5 收件箱点进去）靠 deep link：先切会话，再在右栏定位成员——
  需要 `session.get` 返回成员树（G10.3）。

### 5.1 MU-1 实测形态与原型设想的出入（实现胜出，已回写）

1. **`session.create` 比原型多四个字段**（`cwd` / `initialPrompt` / `budget` / `maxConcurrent`）：原型只画了「题目 + 三张模式卡」；但主进程需要知道工作目录（文件工具/落盘根）与建完即发（S2 的输入框接力），其它两个是团队档可覆盖的显式接口。
2. **`session.escalate` 是超集**：原型只要「单兵 → 团队」（`teamId`）；实测同时允许 `members`（任意临时编队）与换角色，`carryMessages` 缺省 true（已产生的消息不丢）。S2-solo 的提议卡只需用 `teamId` 这一支。
3. **会话事件带**完整快照**不是 patch**：`session.changed` 携带 `SessionSummary`（含 counts/usage/budget），主进程写入 ≤4Hz 节流合并；S1「活跃会话」与左栏列表直接消费，无需再查一遍。
4. **会话级预算事件只在会话自带限额时发出**（团队档或会话档）；纯全局档下只发 `scope:'global'` 事件。否则每个开会话都收到一条与自己无关的重复通知。

## 6. 待用户拍板的开放问题

原型 S3 右侧「待拍板」面板里列的三条，需要在 M4 设计评审前给出结论：

1. **Agent 是团队私有还是全局共享？** 跨团队能否复用同一个 Agent 实体？
   - 私有：模型简单，改一处不影响别队；代价是同一个人配置要复制多份。
   - 共享：复用性好；代价是「本队覆写」要变成引用关系，改动扩散面大。
   - *倾向*：私有（团队 JSON 内嵌成员），复用交给 Agent 类型这一层。
2. **团队能否嵌套？**（子队作为一个成员）
   - 嵌套能表达大型编队，但会让「父∩子白名单」与并发闸门的语义变复杂。
