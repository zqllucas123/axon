## 2. 目标信息架构：屏幕总览

MU 产品化后，单调试屏拆为「**一个全局框 + 六个屏幕**」。分层纪律不变（AGENTS.md §5）：L3 渲染薄壳只做「渲染 + 发意图」，状态真相在主进程；编排决策零残留（现渲染层五组件 715 行即证明其薄度，03 §1 依据 1）。

```
┌────────────────────────────────────────────────────────────┐
│ S0 全局状态条（预算档位 / 挂起审批数 / 熔断警示）【长驻】      │
├──────────────┬─────────────────────────────────────────────┤
│              │ S2 Agent 会话（默认主屏）                    │
│ S1 工作台     │   └ 选中节点的消息流 / 流式 / thinking / 工具卡│
│  ├ 角色面板   │                                             │
│  ├ Agent 树   │ S3 角色管理（S1 内展开或独立）               │
│  └ 会话列表(M5)│ S4 协作账本（M4 新增）                      │
│              │ S5 收件箱（M4 新增）                        │
│              │ S6 预算与用量                                │
│              │ S7 会话恢复（M5 预占位）                     │
│              │ S8 设置（独立设置窗，见 03）                  │
└──────────────┴─────────────────────────────────────────────┘
```

| # | 屏幕 | 对应里程碑 | 现状映射 |
|---|---|---|---|
| S1 | 工作台（角色 + Agent 树） | MU（数据面 M2/M3 已备） | App.tsx 左侧栏（`App.tsx:190-211`） |
| S2 | Agent 会话 | MU（依赖 M6 真模型尖峰定形态） | EventLog 混流 + Composer（`App.tsx:212-230`） |
| S3 | 角色管理 | MU（M2 功能已齐，仅重排） | RolePanel + RoleEditor 模态 |
| S4 | 协作账本 | **M4** | 无 |
| S5 | 收件箱（审批与提问聚合） | **M4** | 无 |
| S6 | 预算与用量 | M4 定协议面（呈现 MU/M6） | 预算 banner（`App.tsx:212-219`） |

> **S8 与本节其余屏幕不同轴**：S0~S7 是「会话/团队」这条主轴的屏幕，S8 是应用级配置，不参与会话切换，也不在左侧栏的 6 项导航里 ——
> 它由独立窗口承载（macOS 惯例：`⌘,` 与菜单栏入口）。完整设计见 [`03-设置界面设计.md`](03-设置界面设计.md)。

## 6. M4 协议扩展的输入汇总（引用 03 §3 M4 关键设计问题逐条对照）

### 6.1 枚举化协作动作 + 落账 → 需要新的协议类型

建议 M4 在协议层新增（文件名布局由 M4 设计评审定，MX 只提形状要求）：

```
type CollabAction = 'consult' | 'fork' | 'delegate' | 'handoff'   // 对齐 01 §6.4 / 02 §3.2
type Adoption = 'pending' | 'adopted' | 'rejected' | 'not_applicable'
interface LedgerRecord {
  id: string; from: AgentPath; to: AgentPath; action: CollabAction;
  forkMode?: ForkModeSpec;      // context_scope 对齐 tutti 02 §3.2
  mention?: string;             // mention://agent-session/<id>，01 §6.4
  adoption: Adoption; usage?: UsageTotals; at: number; status?: ...;
}
```

落账观察点提示（设计输入，非结论）：六编排工具的 execute（`apps/desktop/src/main/orchestrator.ts:148-334`）与 host 驱动封装（`host.ts:509-526` `driverFor`）之间是自然的拦截点——per-spawn 双闭包已把「谁在调用」bind 在 `driver.selfPath`（`orchestrator.ts:44`），from 侧身份零成本可得。`agent.message.received` 事件（G2.1）要么并入账本口径、要么保持轻消息而账本独立——**必须二选一并写进协议**，防止双口径。

### 6.2 mention:// URI 引用
