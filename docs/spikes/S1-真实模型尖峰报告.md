# S1 真实模型尖峰报告

> 状态：**已完成**（2026-09-13）
> 类型：尖峰（spike），非里程碑 ｜ 依据：03 §1「UX 支线定序」配套拍板、§3 M6「⏰ 可提前的尖峰」
> 目标：用真实模型跑通 Axon→pi 全链路，把 faux 掩盖的假设**在 M4 开工前**揭穿

---

## 一、为什么现在做

M0~M3 全程跑在 faux provider 上。faux 的价值毋庸置疑（零成本、可重复、无需 key），
但它有三处系统性失真，而这三处恰好都压在 M4 与 MU（产品化 UI）的设计输入上：

1. **成本恒为 0**：`pi-ai/dist/providers/faux.js:147` 把 `usage.cost` 硬编码归零，
   M3 的预算熔断（BudgetGuard）吃的正是这个字段 —— 也就是说熔断逻辑从未被真数据驱动过
   （M3 期间靠 `withTurnCost` 注水层伪造，见 `packages/kernel/src/provider.ts`）。
2. **工具调用方言未验**：faux 的 toolCall 是我们自己拼的（`fauxToolCall`），
   真模型走的是流式分片 JSON —— pi 能不能拼对，faux 永远答不了。
3. **形态空白**：thinking 通道、流式增量、stopReason 的真实分布，是 MU 信息架构的直接输入。
   拿假数据设计 UI，接真模型必返工（这正是 UI 实现后置的理由）。

## 二、接入方式（代码）

| 位置 | 内容 |
|---|---|
| `packages/kernel/src/provider.ts` | `createOpenAICompatSource(spec)` —— 自定义 baseUrl + 模型清单 + 静态 key auth |
| `apps/desktop/src/main/model-config.ts` | `~/.axon/config.json` + env 覆盖 → `ModelChoice`（faux ｜ openai-compat） |
| `apps/desktop/src/main/index.ts` | `createModelSource()`：配置齐全走真网关，否则**静默降级 faux** |
| `examples/real-model-spike.ts` | 单 Agent 四问（`bun run example:real`） |
| `examples/real-orchestration-spike.ts` | 编排四问（`bun run example:orchestration`） |

三个设计选择值得记录：

- **不复用 pi 内置的 44 个 provider**。企业网关是「自定义 baseUrl × 自定义模型名」的组合，
  `/v1/models` 往往不实现（实测本次网关返回 **404**），内置目录里也不会有这些模型 id。
  与其猜，不如让用户在配置里写清楚 —— 写错立刻 400，比静默走错模型强。
- **key 存 `~/.axon/config.json`（0600），不进 git、不进 env**。走 env 有两个实际问题：
  Electron 从 Finder 双击启动拿不到 shell 环境变量；env 表达不了「模型清单 + 单价 + 默认模型」这种结构。
  系统 keychain 留给 M6 正式接入（引入原生依赖会拖累打包链路，尖峰阶段不值得）。
- **缺配置降级而非报错**。新克隆的仓库、CI、冒烟都应该能直接 `bun run dev`。
  代价是「以为在用真模型其实是假的」，所以启动日志必打 `[desktop] model source: ...` 一行。

## 三、实测结果

网关 `https://gateway.kotei.com.cn/yanjiuyuan/v1`（OpenAI 兼容）。可用模型实测：
`qwen3-max` / `qwen-plus` / `qwen-max` / `qwen-turbo` / `deepseek-v3` / `deepseek-r1`。
（`gpt-*`、`claude-*` 全部 503；`qwen2.5-72b-instruct` access_denied —— 网关只开了部分上游。）

### 幕一：单 Agent 四问（`example:real`）

| 问题 | qwen3-max | deepseek-r1 |
|---|---|---|
| ① 工具调用方言 | ✓ 调用 1 次，分片 JSON 拼接正确 | ✓ 调用 1 次 |
| ② 成本非零 | ✓ `cost.total = 0.000258`（in 120 / out 19） | ✓ `0.000289`（in 263 / out 66） |
| ③ reasoning 通道 | thinking 0 字符（该模型不吐） | ✓ **thinking 422 字符** / text 40 字符 |
| ④ 正常收尾 | ✓ `stopReason = stop` | ✓ `stopReason = stop` |
| 耗时 | 2.5s | 10.3s |

### 幕二：编排全链路（`example:orchestration`，gate=2，真模型自主驱动 M3 六工具）

```
· /root/planner-1              → running
· /root/planner-1/developer-1  → running      ← 模型自己决定 spawn
· /root/planner-1              → waiting      ← 模型自己决定 agent_wait，父退位让额
· /root/planner-1/developer-1  → done
· /root/planner-1              → running      ← 子终态唤醒父
· /root/planner-1              → done
```

| 问题 | 结果 |
|---|---|
| ① 模型会 spawn | ✓ 派生 1 个子 Agent |
| ② role 参数合法 | ✓ `developer`（没有瞎编角色名） |
| ③ 会主动 wait | ✓ 出现 `waiting` —— **没有直接向用户交差**（编排的最大失败模式没有发生） |
| ④ 成本沿父链汇总 | ✓ root `$0.019762` = planner 自身 + developer `$0.016238` |

两次独立运行结论一致（$0.0174 / $0.0198）。

### 幕三：Electron 真窗口（CDP 驱动，走真网关）

```
[desktop] model source: 真模型 kotei/qwen3-max @ https://gateway.kotei.com.cn/yanjiuyuan/v1（key yOX***oa9）
spawn → /root/developer-1
转录：user「一句话说明什么是 ESM-only 包」→ assistant「仅支持 ES 模块语法，不兼容 CommonJS。」
```

IPC → host → 真 provider → 事件 → React 重渲染，全环打通。

## 四、faux 掩盖的四处差异（本次揭穿的）

1. **工具 `execute` 签名是 `(toolCallId, args, signal, ctx)`，第一参不是 args。**
   写成 `(args) => ...` 不会有类型错误（`tools` 那里是 `as never`），只会静默拿到一个
   `call_xxx` 字符串，所有字段都是 `undefined`。`examples/single-agent.ts` 里这个 bug
   潜伏至今没被发现 —— 因为 faux 的回复是写死的，工具参数错了也看不出来。**已修**。
2. **流式增量嵌在 `message_update.assistantMessageEvent` 里，不在顶层。**
   实测事件分布（deepseek-r1）：`thinking_delta` 51 / `text_delta` 5 / `toolcall_delta` 2
   / `thinking_start|end` 各 2 / `toolcall_start|end` 各 1 / `text_start|end` 各 1。
   **这是 MU 流式渲染的接线图**，直接交给 UX 信息架构（MX）。
3. **thinking 是独立的 content block**，与 text 并列在同一条 assistant 消息里
   （实测转录：`assistant thinking+toolCall` / `assistant thinking+text`）。
   UI 需要为它单独设计折叠区，不能和正文混排。
4. **一次编排的真实成本量级：约 $0.02**（qwen3-max，一父一子，四五轮 LLM 调用）。
   M3 熔断的默认阈值、以及 UI 上成本数字保留几位小数，都有了现实参照。

## 五、遗留与后续

- **未验**：长上下文压缩、length 截断续写、流式中断重连（kalo 五个可靠性补丁的对照评估）
  —— 属于 M6 正式接入范围，尖峰不做。
- **未验**：多子 Agent 并发（gate 争用）在真模型下的表现。本次只跑到一父一子；
  M4 的 delegate/handoff 场景会自然压到这条路径。
- **key 管理**：v0.1 明文存配置文件。M7 打包分发前必须换成系统 keychain，
  否则分发出去的应用要求用户明文写 key 是不可接受的。
- **保险丝新增**：`scripts/verify-lazy-loading.mjs` 加了两条断言 ——
  `openai` SDK 不得内联（真 provider 接入后它是最可能被打进来的那个）、
  懒 API 子路径必须保持 external。已用负向测试验证会炸。
