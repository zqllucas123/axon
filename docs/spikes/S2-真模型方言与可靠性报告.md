## 三、实测结果

### 闸口 1：流式增量的真实载荷（B-1/B-3 存活判定）

**结论：B-1（流式文本）存活；B-3（工具增量）存活。两者都要在 M6 接。**

完整事件分布（一轮带工具调用的对话，`deepseek-v4.1-flash`）：

```
assistantMessageEvent 类型分布（共 51 条）：
  text_delta         29   ← B-1 的真实来源
  thinking_delta     10   ← reasoning 通道
  toolcall_delta      4   ← B-3 的真实来源
  text_start          2
  text_end            2
  toolcall_start      1
  toolcall_end        1
  thinking_start      1
  thinking_end        1
```

**增量的真实形状**（host.ts `wire()` 分支的实现规格，每类取首条截断至 200 字符）：

```json
// text_start（首条文本块开始）
{"type":"text_start","contentIndex":0,"partial":{
  "role":"assistant","content":[{"type":"text","text":"I"}],
  "api":"openai-completions","provider":"kotei","model":"deepseek-v4.1-flash",
  "usage":{...}}}

// text_delta（文本增量）
{"type":"text_delta","contentIndex":0,"delta":"I","partial":{...}}

// toolcall_start（工具调用块开始）
{"type":"toolcall_start","contentIndex":1,"partial":{
  "role":"assistant","content":[
    {"type":"text","text":"I'll check the latest build status for axon-desktop."},
    {"type":"toolCall","id":"call_da971dbb5...","name":"lookup_build_status","arguments":{...}}
  ],...}}

// toolcall_delta（工具参数增量，delta 为 JSON 片段）
{"type":"toolcall_delta","contentIndex":1,"delta":"","partial":{...}}

// toolcall_end（工具调用块结束，arguments 已完整）
{"type":"toolcall_end","contentIndex":1,"toolCall":{
  "type":"toolCall","id":"call_da971dbb56d44b4a8781756f",
  "name":"lookup_build_status","arguments":{"service":"axon-desktop"}},...}

// thinking_start / thinking_delta / thinking_end（同结构）
{"type":"thinking_start","contentIndex":0,"partial":{
  "role":"assistant","content":[{"type":"thinking","thinking":"The",
  "thinkingSignature":"reasoning_content"}],...}}
```

**关键细节：**

1. 所有增量**嵌在 `message_update` 的 `assistantMessageEvent` 字段里**（S1 已发现这层嵌套）。
   `wire()` 监听的是 agent 层事件 `message_update`，再从 `.assistantMessageEvent` 取内层。
   `openai-completions.js:601-605` 的 `assistantMessageEvent` 字段名是 pi 内部约定，
   主进程当前完全没有处理这一层（`host.ts:1990` 的 `wire()` 只响应顶层事件类型）。

2. **`thinking` content block 的 `thinkingSignature` 字段值是 `"reasoning_content"`**，
   这是 DeepSeek 系模型对 reasoning 的命名。pi 把它统一归成 `thinking` 类型（
   `openai-completions.js:1329` 的 `thinkingFormat: isDeepSeek ? "deepseek" : ...`）。

3. `toolcall_delta.delta` 首条为空字符串，pi 先发 `toolcall_start`（含 name/id），
   再逐块追加 arguments JSON 片段。拼合由 pi 内部完成，`toolcall_end` 时 arguments 已是完整对象。

### 闸口 2：成本归零根因

**结论：是「配置缺 `cost` 字段」，不是网关不给数。M6 必须在配置校验里补告警。**

对照实验（同一个 prompt，两份 config，仅 `models[0].cost` 有无之差）：

| 条件 | tokens in | tokens out | cost.total |
|---|---|---|---|
| A. 原样（无 `cost` 字段） | 173 | 96 | **0** |
| B. 注入 `{input: 0.27, output: 1.1}` | 40 | 155 | **0.0001813** |

证明：网关照常返回 token 计数（A 组 173+96 非零），pi 用 token 数乘以 model 的 `cost` 单价
（`openai-completions.js:601` 附近的 `calculateCost`），而 `MODEL_DEFAULTS.cost` 全是 0
（`packages/kernel/src/provider.ts:130`），不填就算不出来。

**影响**：S1 当时算出 `$0.000258` 是因为那份 config 里写了 `cost`。
Axon 的 `BudgetGuard` 吃 `usage.cost.total`（`packages/kernel/src/budget.ts:94`）——
用户只要不填 `cost` 字段，M3 的预算熔断整个失效，既无告警也无冻结，且**不报错**。

**修法**（M6 实施范围）：`apps/desktop/src/main/model-config.ts` 的 `resolveModelChoice` 或
`apps/desktop/src/main/index.ts` 的 `createModelSource` 里，对 `model.cost` 全为 0 补一条
`console.warn`，内容形如：
```
[axon] 警告：provider.models[*].cost 均为 0，预算熔断不会触发。如需预算控制请在 ~/.axon/config.json 里填写单价。
```

### 闸口 3：延迟画像（看门狗阈值输入）

**结论：最长静默 1676ms，阈值不低于此的数倍（建议 ≥ 8000ms）。**

```
总时长          5.1s
首个增量        1128ms（从发请求到第一个 text_delta 或 thinking_delta）
最长静默间隔    1676ms（在第 24 帧后，turn_start 事件，即 pi 内部轮次切换时的静默）
事件帧总数      67
```

`turn_start` 和 `turn_end` 之间是 pi 内部「工具结果回注 → 新一轮 LLM 调用」的间隙，
这段时间没有 `message_update`。看门狗如果只盯 `message_update` 帧间隔，会在正常工具回合时误触发。
**看门狗应该盯的是「最后一个 `message_update` 或 `turn_start` 到现在」的静默**，阈值 ≥ 8s。

### 闸口 4：`stopReason=length` 与 pi 自动续写

**结论：网关忽略 `maxTokens` 限制，未触发截断，无法实测 pi 续写行为。**

测试条件：`maxTokens: 48`，要求模型写 800 字以上的长文。
实际结果：模型正常输出（thinking+text 一个回合），`stopReason=stop`，未截断。

根因（两层）：

**第一层：pi 把 `maxTokens` 发到哪个字段由 `compat.maxTokensField` 决定。**
自定义 source 没有 `compat` 字段，pi `openai-completions.js:1325-1337` 回落到 `detected`，
`detected.maxTokensField` 是通过 provider id 推断的（`openai-completions.js:1277-1289`），
自定义 `axon-gateway` provider 不匹配任何已知 id，最终用 `max_completion_tokens`（OpenAI 新字段）。

**第二层：网关可能不识别 `max_completion_tokens`，只认 `max_tokens`。**
kotei 网关后面是 DeepSeek 系模型，DeepSeek 通常用 `max_tokens` 字段（不是 OpenAI 的 `max_completion_tokens`）。
pi 的 `zai-coding-cn.json` 数据显示 DeepSeek-series 均声明 `"maxTokensField":"max_tokens"`。
自定义 source 应该在 model 定义里加 `compat: { maxTokensField: 'max_tokens' }`。

**对 M6 的影响**：

1. `ModelSpec`（`packages/protocol/src/config.ts`）需要增加 `compat?: { maxTokensField?: 'max_tokens' | 'max_completion_tokens' }` 字段，让用户按网关实际能力配置。
2. `provider.ts:172-185` 构造 model 对象时，把 `spec.models[i].compat` 透传下去。
3. `stopReason=length` 的续写补丁：**本次未能实测 pi 是否自动续写**，结论挂起。
   如果网关能正确截断（修了 `maxTokensField` 之后），可以单独再测一次。M6 先把 `compat.maxTokensField` 的透传做进去，续写是否需要额外补丁等实测再定。

### 闸口 5：thinking-only 回合

**结论：本次 2 个 assistant 回合均有 text，无 thinking-only 回合。kalo 补丁 1 暂不需要移植。**

```
assistant 回合 2 个：
  回合 1：text+toolCall
  回合 2：thinking+text
```

`deepseek-v4.1-flash` 在这个任务里 thinking 很短（14 字符），没有出现只有 thinking 没有 text 的情况。
**注意**：这不是一个绝对结论。如果未来遇到更复杂的 reasoning 任务，thinking-only 回合是有可能出现的。
UI 折叠区的「空答复」兜底逻辑（不渲染空 assistant 气泡）是必要的，但 kalo 补丁 1 所描述的「续写」行为（主动 re-prompt）在当前场景下不需要。
