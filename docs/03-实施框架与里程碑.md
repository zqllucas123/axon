## 0. 工作流约定（用户拍板，2026-09-13）

1. **按里程碑推进**，不跳步、不并行两个「改内核」的里程碑（调研/设计类任务除外）。
2. **每个里程碑开工前**，先在 `docs/milestones/M<id>-<短名>.md` 写出「**方案设计 + 实施计划**」（模板见 §4），写完才开始实现。
3. **每个里程碑结束**：`bun run check` 全绿（guard / typecheck / test / build / verify-lazy）、文档同步完成（§5）、一次语义化 commit。
4. 每个里程碑以**一个用户可运行的演示**收尾（`bun run dev` 里能点出来）。
5. 调研文档是交付物的一部分，不是随笔；所有论断带 文件路径:行号。

3. **但 UI 实现必须后置**：(a) §0.4 要求每个里程碑以 `bun run dev` 可点的演示收尾，M4 期间重写 renderer 会砸掉验收面；(b) 现界面本质是**调试控制台**（EventLog 32 行 / AgentTree 43 行），其价值是给 M4/M5 当观测窗口，过早产品化就看不见编排内部状态；(c) 流式输出、thinking、工具调用、真实成本是 UX 最难的部分，faux 下设计必被真模型推翻。

## 3. 规划中的里程碑（预告，细节以各里程碑文档为准）

### M4 协作动作与落账（6.4 MessageBus）
- **用户可见**：两个 Agent 之间可以交接任务（handoff/delegate），每次协作留下一行可查询的账
- **关键设计问题**：
  - 协作动作枚举化（tutti `consult|fork|delegate|handoff`）+ `Adoption` 裁决 + 落账
  - 交接用 `mention://agent-session/<id>` URI 引用，**不拷贝 transcript**（tutti）
  - 审批穿透父级（TabTin `permissions/subagent-hitl.ts:9-17`）
  - 明确不做：把 planning/review 做成特权模型角色（tutti 明示反对）
- **非目标**：通用 pub/sub 总线
- **退出标准预览**：delegate + handoff 场景测试；账本可查询；审批穿透演示

### M5 会话持久化（6.6 TreePersistence）
- **用户可见**：关掉应用再打开，Agent 树、消息、状态完整恢复
- **关键设计问题**：
  - 落盘布局抄 kalo：`sessions/<编码cwd>/<parentSessionId>/subagent/<childId>/*.jsonl`
  - `list_sessions()` **非递归扫描**，天然排除子 Agent
  - 树结构（父子）与单线 JSONL 文件解耦；schema 带版本号（为 M4 账本留扩展点）
  - 中断恢复：pi 无 durable program counter，Axon 侧存状态机状态
- **退出标准预览**：运行中 kill 应用 → 重启 → 树/消息/状态全部恢复；孤儿文件有清理策略

### M6 真实模型接入
- **用户可见**：真实模型跑通单 Agent 与编排，按角色映射模型，成本数字可信
- **关键设计问题**：
  - `ModelSource` 已留 registry 接口 → 接 pi-ai `createRegistry`，faux 保留为测试通道
  - API key 存放（`~/.axon/config` + 系统 keychain）；per-role model 映射
  - **kalo 5 个可靠性补丁对照评估**：查 0.85.1 CHANGELOG 是否已含（thinking-only 续写 / length 自动续写 / 流式看门狗 / 压缩熔断）；缺的用 wrapper 级补救
  - **⏰ 可提前的尖峰**：拿到 API key 就随时插入一次真实模型冒烟——faux 掩盖的方言/delivery 假设只有真实模型能揭穿
  - **✅ 已拍板提前**（2026-09-13）：尖峰在 M4 前后插入，不等 M5。双重动因——除原有的「揭穿 faux 假设」外，MU（产品化 UI）的形态设计依赖真实流式/thinking/工具调用/成本数字，假数据设计必返工
  - 尖峰范围限定：`apps/desktop/src/main/index.ts:50` 的 `createFauxSource` 换成 env 开关（`AXON_PROVIDER`），走 `packages/kernel/src/provider.ts` 边界；faux 保留为测试通道，162 例测试不受影响
- **前置**：用户提供 API key（§6 决策清单 #4）

### MX UX 信息架构（并行支线，纯文档）

## 7. 顺序依据与一个已知权衡

主干顺序 M2→M5 沿用 01 §9（RoleLoader → Orchestrator → MessageBus → TreePersistence）。

一个已知的权衡：**要不要把 M5 持久化提前到 M3 之前**——支持方说编排跑起来后一旦重启即丢，长期调试没有持久化很痛苦（pi durable program counter 为零实现）；反对方说托管 schema 依赖 M4 的账本形状，先定模型后落盘少返工。**决议：维持 01 顺序，但 M5 的 schema 设计必须带版本号并为 M4 账本预留扩展位。** 若 M3 实施中「重启即丢」已经影响日常开发，随时把 M5 整体提前（届时在本文档改状态）。

创建里程碑文档命令约定：`docs/milestones/` 目录，文件名 `M<id>-<短名>.md`（短名用英文小写连字符，如 `M2-role-loader.md`）。
