# Axon 调研补充与结论复核

> 日期：2026-09-12
> 前置：`00-内核选型调研报告.md`、`01-架构决策-方案B.md`
> 方式：三路并行独立核查 —— ①深挖 kalo ②略读 tutti/TabTin ③复核 01 的五条关键论断

## 0. 一句话结论

**架构决策（依赖 pi 包 + 自建编排层 + 全栈 TS）站得住，不推翻。但 01 的五条论据里 1 条不成立、3 条需修正，且出现了一个必须现在就改的默认值决策。**

最重要的三个发现：

1. **🔴 依赖面不薄** —— 实测约 150 个包闭包，含 4 套厂商 SDK 与一个原生二进制依赖。01 §4 的「仅依赖 pi-telemetry」是错的。
2. **🔴 上下文继承的默认值应该是 `none` 而非 `all`** —— tutti / TabTin / kalo 三个产品**互相独立地**收敛到同一结论，其中 TabTin 留下了明确的失败复盘。而 Axon 当前实现默认 `FORK_ALL`。
3. **🟠 "codex 多 Agent 不成熟" 这条论据是错的** —— 它是 `Stage::Stable`、7 个 handler、4 套集成测试，远比 pi 的 AgentHarness（22 个方法全 throw）成熟。放弃 codex 的正当理由只有 WireApi 锁死 + 跨语言成本。

## 1. 五条论断复核结果

| # | 01 中的论断 | 判定 | 要点 |
|---|---|:--:|---|
| 1 | pi-ai/pi-agent-core 依赖面薄 | **不成立** | 见 §1.1 |
| 2 | pi 官方拒绝 subagent，不会有上游支持 | 部分成立 | 事实对，推论错，见 §1.2 |
| 3 | AgentOptions 钩子够用，不必改源码 | **成立** | 但主力机制写错了，见 §1.3 |
| 4 | 锁版本即可控制上游变动风险 | 部分成立 | 风险是迁移税不是漂移，见 §1.4 |
| 5 | codex WireApi 只剩 Responses / multi_agent_v2 不成熟 | 前半成立<br>后半**不成立** | 见 §1.5 |

### 1.1 依赖面（论断 1 —— 不成立）

`pi-ai@0.85.1` 的 `dependencies` 有 10 项，其中 4 个是完整厂商 SDK
（`node_modules/@earendil-works/pi-ai/package.json:59-70`）：

```
@anthropic-ai/sdk 0.123.0 · openai 6.40.0 · @google/genai 1.52.0
@aws-sdk/client-bedrock-runtime 3.1048.0   ← 整套 AWS SDK v3
@smithy/node-http-handler · http(s)-proxy-agent · partial-json · typebox
```

`pi-agent-core@0.85.1` 还依赖一个 01 完全没提到的包
（`node_modules/@earendil-works/pi-agent-core/package.json:55-63`）：

```
@earendil-works/chord ^0.85.1   →  依赖 esbuild@0.28.1（带平台原生二进制）
```

`node_modules/.bun/` 下实际扁平化闭包约 **150 个包**，含 `@aws-sdk/*`（20+）、
`@smithy/*`（10+）、`protobufjs`、`google-auth-library`、`@esbuild/darwin-arm64`。

**仍然成立的三点（好消息）**：
- ✅ 不需要装 pi 全家桶 —— `node_modules/@earendil-works/` 下确实只有两个包
- ✅ 无 `peerDependencies` / `optionalDependencies`
- ✅ provider 懒加载 —— `pi-ai/dist/index.js:2` 只导出 `api/lazy.js`，`lazy.js:46-49` 动态 import；AWS/Google SDK **装了但不进内存**
- ✅ `esbuild` 只被 `chord/dist/node/bundle.js:4` 引用，主入口路径用不到，运行时不加载

**结论**：能独立依赖 ✅，但"薄"❌。真正的代价在**打包阶段**，见 §4 风险 2。

### 1.2 上游支持（论断 2 —— 事实对，推论错）

README 原文确认（`agents/pi/packages/coding-agent/README.md:498-500`）：
`**No MCP.**` / `**No sub-agents.** There's many ways to do this... or build your own with extensions`。

但「不会有上游支持」被三条反证推翻：

1. **pi 官方维护 first-party subagent 扩展并持续修 bug** ——
   `packages/coding-agent/examples/extensions/subagent/`，含 scout/planner/reviewer/worker
   四个 agent 定义与 chain/parallel 两种编排模式；CHANGELOG 里相关修复至少 7 条。
2. **harness 的 Lane 抽象就是为 subagent 设计的** ——
   `packages/agent/docs/harness.md:98`：`Additional lanes support Slack threads, subagents,
   and other parallel work over shared history.`
3. 「拒绝」的语义是**不内置进 CLI**，不是不提供能力。

`agent-harness.ts` 的实现度也数清楚了（**约 510 行**，非 01 暗示的规模）：
22 处 `HarnessNotImplemented`，被 throw 的是全部行为方法，其中
**`lane` / `createLane` / `lanes` 三个多 Agent 关键 API 全在里面**（L445/448/451）；
真正实现的只有约 15 个内存态 getter/setter。设计文档 `harness.md` ≈2943 行。

> **2026-09-16 复查修正（M5 收口时）**：同一 fork 的当前工作树上，`harness/agent-harness.ts` 是 **508 行 / `HarnessNotImplemented` 5 处**（`kalo-harness/node_modules/@earendil-works/pi-agent-core/src/harness/agent-harness.ts`）—— 原记录的「22 处」与今天这个数字对不上（口径不同或上游已改），**结论不变**（行为方法仍大量未实现）。另补一条 kalo 事实细修：**会话落盘的写侧在 pi fork 的 TS 里，不在 Rust** —— `harness/session/jsonl/repo.ts:109` 的 `JsonlSessionRepo`（247 行，`create`/`open`/`list`/`delete`/`fork`）负责写入与 fork；Rust 侧 `kalo-desktop/src-tauri/src/sessions_store.rs` 只做**列表/删除/改名**（`:36` `list_sessions`、`:106` `delete_session`、`:128` `rename_session`、`:251` `parse_session_file`）。这条印证了 Axon 的取舍：不复用 `JsonlSessionRepo`（托管 schema 与我们的分层冲突），自建 `session-files.ts` + `session-persistence.ts`。

**正确表述**：多 Agent 不会以 CLI 内置功能出现，**但上游正在建 lane-based harness 作为多 Agent
底座**。自建编排层的正确姿势是**对齐 pi 的 extension/tool 模型与 lane 语义**，而非另起炉灶。

### 1.3 钩子（论断 3 —— 成立，但主力机制写错了）

七个钩子全部存在，签名核对通过（`packages/agent/src/agent.ts:98-123`）。
`AgentEvent` 确实 10 种（`types.ts:428-449`）。
注意 `streamFn` 是**必填**（0.81.0 的破坏性变更）。

**关键问题「能否挂起 turn 等子 Agent 完成」—— 能，三条路径：**

| 路径 | 机制 | 证据 |
|---|---|---|
| **A（首选）** | 自定义 `AgentTool.execute()` 是被 await 的 | `agent-loop.ts:679` `await prepared.tool.execute(...)`；官方 subagent 示例即此法 |
| B | `beforeToolCall` 是 async 且被 await | `agent.ts:106` |
| C | `subscribe()` 监听器被**串行 await** | `agent.ts:588-590`；文档明示 agent 在监听器 settle 前不会 idle |

配合 `prepareNextTurnWithContext` 返回 `AgentLoopTurnUpdate { context?, model?, thinkingLevel? }`
（`types.ts:138-145`），子 Agent 产出可整个替换父 Agent 下一轮 context，甚至换模型。

> **需要改 01 的措辞**：「挂起—等待—续跑」的主力是 **`AgentTool.execute()` 的 async 语义 +
> `prepareNextTurnWithContext` 的 context 注入**，钩子是辅助（拦截/改写/止损）。
> **tool 才是编排的主干。**

### 1.4 版本风险（论断 4 —— 部分成立）

最近 5 个 minor（0.80→0.84）中 **4 个含 `### Breaking Changes`**：

| 版本 | Breaking |
|---|---|
| 0.84.0 | 4 条 —— 换 v4 lane-based Session、v2 harness 转正并**删除 experimental 子路径** |
| 0.83.0 | — |
| 0.82.0 | 替换 `AgentHarness` 的 `ExecutionEnv` 与 `AgentTool` 输入契约 |
| 0.81.0 | 3 条 —— **`streamFn` 可选→必填**、`uuidv7` 导出迁移、`SessionStorage` 契约变更 |
| 0.80.0 | ✅ |

**`AgentOptions` 在最近 5 个版本里被动过 3 次**，其中 `streamFn` 两周内反复了两次。
节奏约 **2 个月 7 个 minor**，patch 常常同日多发。
`pi-ai` 的 `[Unreleased]` 里**已排队一条 Breaking**（`GoogleThinkingLevel` 改名）。

Axon 已锁精确版本 `"0.85.1"`（无 `^`）✅。但真实成本不是"会不会漂"，而是
**每次要拿 bugfix / 新模型支持就付一次迁移税，约 2 周一次**。而 `pi-ai` 的模型目录更新
（新模型、新价格、国内模型）正是选它的核心价值，长期钉死不现实。

> ⚠️ 盲区：本地 pi 源码 checkout 是 **0.84.2**，而 Axon 装的包是 **0.85.1**，
> 所有基于本地源码的验证都存在一个 minor 的偏差。

### 1.5 codex（论断 5 —— 前半成立，后半不成立）

**WireApi（成立，且是最硬的理由）** —— `codex-rs/model-provider-info/src/lib.rs:60-67`
枚举**只有一个变体** `Responses`，且手写 Deserialize 把 `"chat"` 变成显式报错（`:78-88`）。
连本地 Ollama / LM Studio 都被强制走 Responses（`:516,520`）。

**multi_agent_v2（不成立，必须修正）** —— `codex-rs/features/src/lib.rs:1118-1123`：

```rust
FeatureSpec { id: Feature::MultiAgentV2, key: "multi_agent_v2",
              stage: Stage::Stable,        // ← 不是 Experimental
              default_enabled: false }
```

`Stage::Stable` 的注释是"flag 保留只为 ad-hoc 开关"。且 `Feature::Collab`（multi_agent v1）
是 `Stable + default_enabled: true`，**已默认开启**。成熟度佐证：7 个 handler、
5 个运行时模块（registry/control/role/status/agent_resolver）、4 套集成测试
（含 resume/中断/并发）、可配置并发上限、`MultiAgentMode`/`SpawnCsv` 已被 `Stage::Removed`
清理掉（说明这条线经历过收敛而非乱试）。

> **必须从 01 删掉的论据**：不要再用「codex 多 Agent 不成熟」论证放弃 codex。
> 用错误论据做对的决策，会在下次评审时被质疑，也掩盖了真实权衡。
> 保留的正当理由只有两条：**WireApi 锁死非 Responses 模型** + **Rust/TS 跨语言成本**。

## 2. kalo：pi 内核桌面化的现成范本

kalo = Tauri v2 + React，子进程驱动 `pi --mode rpc`，`kalo-harness/` 是 vendored pi 0.84.1。

### 2.1 ⭐ 最关键的一条：RPC 协议是单会话的

`coding-agent/src/modes/rpc/rpc-mode.ts:58-62`：

```ts
export async function runRpcMode(runtimeHost) { let session = runtimeHost.session;
```

**协议里不存在任何 session/agent 标识参数**，`runRpcMode` 直接接管 stdout 绑定单例 session。
kalo 的并发靠**多开进程**实现（`session.rs:20-27` 的 `HashMap<String, PiProcess>`）。

**对 Axon 的意义**：多子 Agent 协作在 RPC 协议层**无路可走**，必须 in-process。
这**反向验证了 01「直接依赖 `pi-agent-core` 库」的选型是对的** —— 而且比 01 自己给的理由更硬。

### 2.2 vendored 还是 npm 依赖？—— "零改动"有条件成立

kalo fork 了 pi，但对 core 只打了 **5 处补丁，全是可靠性性质，无一是功能性质**：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `harness/tools/grep.ts:79-85` | `query` 作为 `pattern` 的别名（弱模型常写错参数名） |
| 2 | `agent-loop.ts` | thinking-only 轮次注入 continuation；`stopReason==="length"` 自动续写 |
| 3 | `api/anthropic-messages.ts:316-320` | 流式空闲看门狗 60s，防网关半死连接挂死一轮 |
| 4 | `core/agent-session.ts:1932-1978` | 压缩熔断器 + `savingsRatio >= 0.15` 有效性判定 |
| 5 | 同上 `:166,341,2123` | `compaction_end` 事件扩字段 |

**功能增量 100% 走 extension**（12 个内置扩展），只为 permission 往 core 加了一个 RPC 命令
（`rpc-mode.ts:702-713` 的 `set_permission_mode`）—— 理由写在
`doc/2026-09-07-权限模式.md:279-283`：写进 core 会「显著推高 vendored 引擎同步上游的成本」。

**结论**：Axon 的"纯 npm 依赖、零源码改动"可行。若这些可靠性修复已在 0.85.1（需查 CHANGELOG），
或愿意用 wrapper 绕过，就不需要 fork。

### 2.3 kalo 的 subagent 实现 —— 与 Axon 最直接可比

`coding-agent/src/extensions/subagent/index.ts`：

| 机制 | 做法 |
|---|---|
| 进程形态 | **in-process** `createAgentSession`，非子进程 |
| **上下文传递** | **只传 `prompt` 文本，不复制父消息历史** |
| 模型面接口 | 单工具 `agent(prompt, description?, tools?, resume?)` |
| 工具裁剪 | `DEFAULT_TOOLS = ["read","grep","glob","ls","web_fetch"]` |
| 递归防护 | `noExtensions: true` + 显式注入 webfetch（切断递归 spawn / MCP） |
| 并发 | 进程级信号量 6；**resume 跳过信号量以避免死锁** |
| 活性 | `IDLE_TIMEOUT_MS = 5min`（按空闲而非总时长） |
| 输出 | `MAX_RESULT_CHARS = 16_000`，实时 `onUpdate` 活动流上限 2000 字 / 200 条 |
| 常驻 | `Map<childId, ChildHandle>` LRU 上限 16 |
| 完成判定 | `waitForIdle()` 等 `agent_end && !willRetry`（`followUp()` 入队即返回） |
| 失败 | provider 错误以 `stopReason:"error"` 的 assistant 消息到达，**不 throw** |

明确的非目标（`doc/2026-09-11-可续写子agent与主agent派生.md`）：
**不递归 spawn、不做 agent 间直接通信、引擎重启不自动复活**。
—— 这三条恰恰是 Axon **要做**的，说明 pi 原生不支持，MessageBus / 递归编排必须由 Orchestrator 层自建。

### 2.4 落盘布局（可直接抄）

```
~/.kalo/agent/sessions/
  <编码后的 cwd>/                      # 如 --Users-foo-proj--
    <时间戳>_<session-id>.jsonl        # 顶层会话
    subagent/
      <parentSessionId>/
        <时间戳>_<childId>.jsonl       # 子 agent 会话
```

JSONL 首行 `{"type":"session","id","timestamp","cwd"}`，其后每条带 `parentId` 指向上一叶子，
构成 append-only 父链树。

**极低成本的巧思**：`sessions_store.rs` 的 `list_sessions()` **非递归扫描**，
`subagent/` 子目录天然被排除在会话列表外 —— 子 agent 不污染主列表，零额外代码。

**分页不能从文件尾倒读**（`doc/2026-08-15-fast-history-and-file-panel.md:27-29`）：
分支链在 compaction/fork 后可指向文件任意靠前位置。
kalo 的做法是遍历所有带 id 条目，用 `serde_json::value::RawValue` 只解析行头。

### 2.5 Tauri v2 的真实代价

- **19 个 Rust 模块**把 FS/git/知识库/记忆/技能/MCP/会话分页**全部重写一遍**，
  尽管子进程里就有完整 Node 运行时
- **IPC 类型同步 = 手抄 + 机检**：`scripts/check-bridge-contract.mjs` 比对
  `pi-bridge.ts` 的 `invoke("x")` 与 `main.rs` 的 `generate_handler![...]`
- **同步命令冻 UI**：`doc/2026-08-17-ui-responsiveness.md:20-40` —
  「37 个 `#[tauri::command]` 无一是 async…主线程即窗口事件循环」
- **打包欠账**：未配 updater；版本号散落 5 处靠脚本文本替换；
  **无 Apple 签名公证**；`doc/2026-08-19-生产级差距诊断.md:128-132` 自评
  「只覆盖 Windows，会砍掉很大一块想 fork 的人」

> 没有找到「后悔选 Tauri」的直接表述，但代价清单足够明确。
> Axon 若选 Electron，这 19 个 Rust 模块的工作量归零（直接用 Node），
> 代价是安装包体积 —— 而 §1.1 已经指出依赖闭包本来就重。

## 3. tutti / TabTin：两个已成型的协作模型

### 3.1 ⭐⭐ 最重要的发现：上下文继承的默认值

**TabTin 有和 Axon 几乎一一对应的抽象**
（`TabTin/packages/agent-wire/src/speaker.ts:19-29,48`）：

```ts
InheritMode = 'full' | 'filtered' | 'summary' | 'none'
source      = 'template' | 'inherit' | 'blank'
```

—— `template`=角色模板、`inherit`=继承父上下文、`blank`=纯净。**这就是你的需求原型。**

**但他们最终把默认值改成了 `none`**
（`packages/agent-runtime/src/subagent/fork-query.ts:82`）：

```ts
const DEFAULT_INHERIT_MODE: InheritMode = 'none';
```

理由写在 `:70-80`，是一份实打实的失败复盘：

> filtered 继承会把父原文「调 N 个 agent 做 X」灌进子上下文，
> **弱模型被父原文带跑，thinking 里反复纠结「父原文 vs 自己的 directive」**。

子 Agent 的输入 = system prompt（worker 纪律）+ 父派的 task，
**不掺父会话背景、不加 `<fork-boilerplate>` 包裹噪音**（`:84-98`）。
`fork_context: boolean` 作为显式逃生门。三级嵌套（`MAX_SUBAGENT_DEPTH = 2`）
是在 `none` 的保护下才敢保留的。

**三个产品独立收敛到同一结论**：

| 产品 | 默认上下文策略 | 证据 |
|---|---|---|
| TabTin | `none`（从 filtered 改回来的，带复盘） | `fork-query.ts:82` |
| kalo | 只传 prompt 文本，**不复制父历史** | `extensions/subagent/index.ts` |
| tutti | 手动派发必须**显式选** `none/recent/full`，无默认 | `collabrun/model.go:130` |

> 🔴 **Axon 当前实现与此相反**：`packages/protocol/src/agent.ts` 的
> `parseForkMode()` 注释写着"undefined → all（继承全部，最不意外的默认）"。
> 这个默认值建议反转，见 §5 决策 1。

### 3.2 tutti：协作动作枚举化 + 反对"特权角色"

- **协作动作只有四种，且都落账**：
  `collabrun.Mode = consult | fork | delegate | handoff`（`biz/collabrun/model.go:17-27`），
  落库 `collaboration_runs` 表含 `context_scope / adoption / usage`
- **交接载体是 URI 引用而非 transcript 拷贝**：`"mention://agent-session/" + sessionID`
- **`Adoption = pending | adopted | rejected | not_applicable`** —— consult/delegate 默认等人表态
- **明确反对把 planning/review 建成特权模型角色**
  （`docs/architecture/workspace-agents-and-automation.md:459` What To Avoid）
- 配置层 `WorkspaceAgent`（"不是模型角色"）与运行层 `Session`（树形）严格分离
- Session 树的父子边由「哪个 turn 的哪次 tool call 派生」定义（`session_types.go:288-293`）
- 上下文四套机制分清：`ContextScope`(none/recent/full) / `SessionForkLineage`(持久 fork)
  / `Side`(零持久化临时分支) / `SessionIsolation`(git worktree 文件级隔离)

### 3.3 TabTin：角色与权限的双正交建模

- **`AgentMode` × `ApprovalMode` 双维度**（`packages/agent-modes/src/types.ts:21-28,70-74`）：
  - `ask | agent | plan | study | yolo | **group**` —— **`group` 就是 PMO 模式：
    主 Agent 做项目管理者调度角色化子 Agent**，正是 Axon1 的原型
  - `always_ask | auto | full_access` —— 注释明说「AgentMode 管做什么类型的事，
    ApprovalMode 管多大程度放手」
- **角色是声明式 JSON 包**：`packages/agents/code-engineer/agent.json`
  （persona / initial_rules / skills / default_mode）
- **一个 `agent` 工具承担全部子 Agent 生命周期**（`subagent/agent-tool.ts:126-232`）：
  `background`（异步立返）→ `wait_agent_ids`（挂起等终态）→ `check_agent_id`（只读查，带节流）
  → **`message_agent_id`（运行中投递指令，下一轮生效）** → `resume_agent_id` + `interrupt`
- **子 Agent 的审批穿透到父级**：`createSubagentUserInteractiveChannel` 包装父 channel，
  `askHint` 注入子 Agent 标识让对话框显示「由子 Agent 发起」
  （`permissions/subagent-hitl.ts:9-17`）；挂起保护：>100 pending 直接 deny，单请求 1 小时超时
- 受限模式有 **shell input 级白名单**（只放行 `Risk=RiskNone` 的 CLI）

## 4. 风险登记（更新 01 §8）

| 风险 | 等级 | 变化 | 应对 |
|---|---|---|---|
| **上游 harness 重写与自建编排层正面碰撞** | 🔴 **新增·最高** | 01 未识别 | 见下 |
| **依赖体积与 Electron/Tauri 打包** | 🟠 **新增** | 01 因论断 1 出错而漏掉 | 见下 |
| 版本升级迁移税 | 🟡 上调 | 01 低估为"锁版本即可" | adapter 隔离 + 契约测试 + 节奏预留预算 |
| 按消息切片导致孤儿 toolResult | ✅ **已解决** | `fork.ts` 已实现 round 切分 + repair，44 测试通过 | — |
| 多 Agent token 成本失控 | 🟡 保持 | — | Registry 并发上限 + 预算熔断 |

### 🔴 风险 A：上游 harness 重写

pi 正在把执行内核从 `Agent`（当前能用）迁向 `AgentHarness` + lane-based Session
（当前 22 个方法全 throw）。0.84.0 已把 v2 harness **提升为默认导出并删除 experimental 子路径**，
而 `createLane`/`lane`/`lanes` —— **正是 Axon 要自建的那层能力** —— 还没实现。

两个坏结局同时存在：
- 若基于 `Agent` 建编排层，上游完成 harness 后 `Agent` 可能被降级/弃用 → 编排层整体重写
- 若上游 lane 语义（共享 entry tree、durable operation、crash recovery）与 Axon 自建模型冲突
  → 迁移不是加胶水而是换底座

**立刻要做的三件事**：
1. 把对 `pi-agent-core` 的调用**收敛到一个 adapter 模块**，不让 `Agent` 类型泄漏到编排层
2. 读完 `packages/agent/docs/harness.md` 的 lane 章节，让自建编排的概念模型**主动对齐 lane 语义**，
   把未来迁移变成「换实现」而非「换设计」
3. 盯 `createLane` 何时落地

### 🟠 风险 B：打包

未验证的具体问题：
- Electron/vite 打包时 `pi-ai/dist/api/lazy.js` 的动态 `import()` **能否被保留为运行时懒加载**？
  若被 bundler 静态提升，安装包会从「几 MB」变「几十 MB」，且把 4 套 SDK 全塞进主进程
- `@esbuild/darwin-arm64` 等平台二进制在 macOS 公证 / Windows 跨平台构建中的处理
- `engines: node >=22.19.0` 与目标 Electron 内嵌 Node 的兼容性

Axon 当前 `package.json` 只有 `example:single` 一个脚本，**没有任何打包配置**，
这个风险完全没被触及过。**建议尽早做一次最小打包冒烟测试**，测体积 + 验 provider 懒加载存活。

## 5. 需要拍板的三个决策

> ✅ **2026-09-13 已拍板**：决策 1 按建议执行（默认 `none`，已实现并加回归测试）；
> 决策 2 选 Electron（已实现桌面壳 + IPC 往返实测）；决策 3 用户选择直接开发
> Electron（内核层与桌面壳交替推进，未先做独立 CLI，但 AxonHost 保持 electron-free，
> 可由测试/脚本 headless 驱动——CLI 的好处以另一种形式保留）。

### 决策 1 🔴：ForkMode 的默认值反转为 `none`

- **现状**：`packages/protocol/src/agent.ts` 的 `parseForkMode(undefined)` → `FORK_ALL`
- **证据**：TabTin 从 filtered 改回 `none` 并留下复盘（`fork-query.ts:70-82`）；
  kalo 只传 prompt 不传历史；tutti 强制显式选
- **建议**：默认 `none`；`all` 保留为显式逃生门；同时为子 Agent 定义**结构化 task 契约**
  （不是把父原文灌过去）
- **代价**：与用户原始表述「可选纯净 or 继承全部」的语感略有出入，但两个选项都还在，只是默认值换了

### 决策 2 🟠：前端形态 Electron vs Tauri（01 §7 待定项 1 的升级版）

新增的判断依据：
- kalo 选 Tauri 的代价是 **19 个 Rust 模块重写 Node 已有能力** + 手抄 IPC 契约 + 无签名公证
- Axon 的依赖闭包本就重（§1.1），Tauri 的"体积小"优势被 pi 的依赖抵消了一部分
- Axon 内核必须 **in-process 跑 pi**（§2.1），而 pi 是 TS —— Electron 可直接 import，
  Tauri 则**必然**要么走子进程要么内嵌 Node

> 倾向：**Electron**。因为 §2.1 已经证明多 Agent 必须 in-process，
> 而 Tauri + in-process TS 内核是矛盾的。

### 决策 3 🟡：先 CLI 还是直接 GUI（01 §7 待定项 1 的原题）

kalo 的经验说明 GUI 那一层（运行时池、事件分发、批渲染、崩溃恢复）
是**全仓最大最容易失控的文件**（`chat-store.ts` 1405 行，被列入质量棘轮基线）。
建议仍按 01 的倾向：**先 CLI 跑通编排语义**，把 6.1/6.2/6.3 验证完再上 GUI。
