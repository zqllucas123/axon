> ## ⚠️ 结论已变更
>
> 本报告推荐的「codex 作内核」**已被推翻**，最终决策见 `01-架构决策-方案B.md`。
>
> **最终方案**：直接依赖 `pi-ai` + `pi-agent-core` 作为执行内核，自建多 Agent 编排层，全栈 TypeScript。
>
> 变更原因（本报告的分析本身仍然有效，是决策权重变了）：
> 1. codex 是**产品**不是库，多 Agent 编排是 Axon 的核心价值，不应寄生于他人的 feature flag
> 2. codex 的 Responses-API-only 是硬伤，而 pi 的 `packages/ai`（44 provider / 31 方言 / 12 个国内模型）正是解药
> 3. 实测确认 `pi-ai` 与 `pi-agent-core` **可独立依赖**（仅依赖 pi-telemetry + 4 个小库，全 MIT），无需重写 L0/L1
> 4. 本报告给 pi 的 6.5 分扣在「无多 Agent 编排」——但那部分恰是 Axon 要自建的差异化资产，对本项目不构成扣分项
>
> **本报告仍然有价值的部分**：codex 的 `multi_agent_v2` 设计（spawn/fork_turns/角色系统/AgentPath）是本问题域已验证的图纸，Apache-2.0 允许借鉴，Axon 的编排层据此设计。

## 0. 一句话结论

**codex 是 Axon 的最佳内核底座（9/10）**——因为你提出的"多角色子 Agent 协作"和"纯净分身 / 全继承分身"两个核心诉求，**在 codex 里已经是一等实现，不是需要自己造的东西**。

| 产品 | 定位 | 适配度 | 一句话 |
|---|---|:--:|---|
| **codex** (OpenAI) | Rust Agent 运行时 + GUI 后端协议 | **9/10** | 需求几乎逐条命中，但接非 OpenAI 模型要补适配层 |
| **agent-framework** (Microsoft) | Python/.NET 编排 SDK | **8.5/10** | 编排能力最强、声明式最完备，但要自己写产品级客户端 |
| **pi** (earendil) | TypeScript 单 Agent 内核 | **6.5/10** | 底层做到极致，**但官方明确拒绝做子 Agent 和 MCP** |

## 2. 逐条对照你的需求

### 需求①：定义多个角色化子 Agent（Axon1~5）

| | codex | agent-framework | pi |
|---|---|---|---|
| 支持度 | ✅ **一等实现** | ✅ 强 | ❌ 官方 non-goal |
| 机制 | `agent_roles` 配置系统 | 5 种 orchestration 模式 | 仅 example 扩展 |

**codex 的实现方式（关键发现）**：往配置目录的 `agents/` 里丢一个 TOML 文件，就声明了一个角色——**不需要写代码**。

```
core/src/config/agent_roles.rs:20   load_agent_roles()  — 从各配置层的 agents/ 目录发现角色
core/src/agent/role.rs:36-48        AgentRoleOverrides — 每角色可独立指定：
                                      developer_instructions / model / reasoning_effort
                                      / personality / features / skills
core/src/agent/builtins/            内置角色示例：awaiter.toml、explorer.toml
```

这意味着 Axon1(进度)/Axon2(架构)/Axon3(开发)/Axon4(测试)/Axon5(人机对齐) 可以直接落成 5 个 TOML 文件，各自配不同模型和工具权限——**Axon5 可以禁掉 shell 工具只留对话，Axon3 给最强模型**。角色系统还有"只能减能不能越权"的安全约束（`role.rs:91-106`）。

**pi 的态度**是明确拒绝：README 原文 "**No sub-agents.**"、"**No MCP.**"。它设计了 Lane 多泳道模型，但 `harness/agent-harness.ts` 几乎所有方法都是 `throw HarnessNotImplemented`——**2941 行设计文档，零行实现**。这是选型时最大的陷阱：按文档评估会严重高估。

### 需求②：纯净上下文分身 vs 继承全部上下文分身

**这是三者差异最大的一项，也是 codex 得分最高的原因。**

codex 的 `spawn_agent` 工具直接有 `fork_turns` 参数：

```
core/src/agent/control.rs:70-73
    enum SpawnAgentForkMode { FullHistory, LastNTurns(usize) }

core/src/tools/handlers/multi_agents_v2/spawn.rs:284-309
    fork_turns = "none"  → 不传父历史        ← 你要的「纯净轻量分身」
    fork_turns = "all"   → FullHistory       ← 你要的「继承内核全部上下文」
    fork_turns = "3"     → LastNTurns(3)     ← 额外赠送：部分继承
```

**你描述的两种分身模式，在 codex 里是一个字符串参数的事。** 而且多送了一档"继承最近 N 轮"的折中模式——实际产品中这一档往往最实用。

agent-framework 也原生支持（有三处独立机制，`AgentExecutor` 的 `context_mode` 等），pi 则只有写死的 `--no-session`。

### 需求③：子 Agent 协同工作

codex 提供完整的 Agent 间通信设施，六个工具构成闭环：

```
core/src/tools/handlers/multi_agents_v2/
  spawn.rs            派生子 Agent
  send_message.rs     Agent 间发消息
  wait.rs             等待子 Agent 完成
  list_agents.rs      列出当前活跃 Agent
  interrupt_agent.rs  中断某个子 Agent
  followup_task.rs    向已有 Agent 追加任务
```

配套：`AgentPath` 路径寻址（形如 `/root/task1/task_3`，天然支持 Agent 树）、`InterAgentCommunication` 消息协议、`subagent_start`/`subagent_stop` 生命周期 hooks、`default_subagent_model` 全局默认模型配置、`agent_max_threads` 并发上限。

agent-framework 走的是另一条路——**图编排**：sequential / concurrent / handoff / group_chat / magentic 五种成熟模式 + 通用图执行引擎 + checkpoint + human-in-the-loop。如果 Axon 的协同是"固定流程编排"（需求→架构→开发→测试的流水线），MAF 的表达力更强；如果是"主 Agent 动态决定派谁去做"，codex 的模型更自然。

### 需求④：Axon5 人机交互对齐

codex 有现成工具：`request_user_input`（主动向人提问）、`request_permissions`、`ExecApprovalRequest`（执行前审批）。MAF 有 `request_info` + `@response_handler` 的 HITL 机制。pi 有扩展 hook 但需自建。

## 3. 客户端形态：谁能当 GUI 后端

Axon 是**客户端产品**，这一项权重很高。

**codex —— 最成熟**：`app-server` 是专门为 GUI 前端设计的 JSON-RPC 后端，约 230 个方法，支持 stdio / unix socket / websocket 三种传输；`app-server-protocol` 用 `ts-rs` **自动导出 TypeScript 类型定义**。

```
app-server-protocol/src/rpc.rs:1-84            JSON-RPC 信封
app-server-protocol/src/protocol/common.rs:487 方法注册表
app-server-protocol/schema/typescript/         已生成的 TS 类型（含 SubAgentActivityKind 等）
app-server/src/main.rs:28-35                   传输方式选项
```

**这是理想架构**：Axon 用 Electron/Tauri 写前端 → spawn `codex app-server` 子进程 → JSON-RPC 通信 → TS 类型直接从 Rust 生成，前后端类型永不失配。Rust 内核不用改一行，Axon 的差异化全在前端和角色配置上。

**agent-framework**：只有 DevUI（官方标注"非生产用途"）和一个 Textual TUI 示例，产品级客户端要自己写。
**pi**：TUI 是纯终端渲染，GUI 场景整体丢弃；但有 SDK + JSON + RPC(32 方法) 通路。

## 4. 各自的关键短板

**codex**
- ⚠️ **最大风险**：`WireApi` 已删除 Chat Completions，**只保留 OpenAI Responses API**（`model-provider-info/src/lib.rs:63-67,86`）。接 Claude/Gemini/国内模型需自建适配层。
- Rust 上手成本高，`core` 单 crate 32 万行，改造需要真正的 Rust 能力。
- 多 Agent 在 `multi_agent_v2` feature flag 后面，属于较新特性。

**agent-framework**
- 不是产品是 SDK，产品级客户端从零写。
- 缺 LSP/AST 级代码库理解、diff/patch 引擎、git 集成（`_harness/` 自带的执行面只覆盖文件读写/shell/todo）。
- API 变动大：网上教程里的 `AgentThread`/`ChatAgent`/`@ai_function` 在当前版本已全部改名。

**pi**
- 多 Agent、MCP 都是官方明确的 non-goal，两项都得自建。
- 崩溃恢复只有设计没有实现（durable program counter 零实现）。
- **但它的 `packages/ai` 是全场最强资产**：40 个 provider / 15 种 API 方言 / 3.5 万行测试。

## 5. 选型建议

### 主推方案：codex 作为内核 + Axon 自研前端

```
┌─────────────────────────────────────────┐
│  Axon 客户端 (Electron/Tauri + TS)       │  ← 你的差异化：多 Agent 可视化、
│  - Agent 树可视化 / 分身创建 UI          │     角色编辑器、进度看板
└──────────────┬──────────────────────────┘
               │ JSON-RPC (stdio)，TS 类型由 ts-rs 自动生成
┌──────────────▼──────────────────────────┐
│  codex app-server（子进程，几乎不改）     │
└──────────────┬──────────────────────────┘
┌──────────────▼──────────────────────────┐
│  codex core：多 Agent 树 / 角色系统 /     │
│  fork 策略 / 沙箱 / 工具 / 持久化          │
└─────────────────────────────────────────┘
      ▲
      └── ~/.axon/agents/*.toml  ← Axon1~5 五个配置文件，纯声明
```

**为什么推荐**：你需求里最难自研的部分（多 Agent 树、上下文 fork 语义、沙箱、审批、持久化、断点续跑）codex 全都有生产级实现；你要做的是**前端体验和角色设计**——正是产品差异化所在。改造量最小，起点最高。

**先验证的两件事**（决定方案成败）：
1. **模型接入**：Responses API 限制对你是否致命。若必须接国内模型/Claude，先做 PoC 验证适配层成本——这是唯一的硬风险。
2. **`multi_agent_v2` 实跑**：打开 feature flag，手写 2 个角色 TOML，验证 spawn + fork_turns=none/all 的真实行为。

### 备选方案：agent-framework
如果团队是 Python 栈、且协同流程偏"固定编排"而非"动态派发"，MAF 的图引擎 + checkpoint + 声明式 YAML 更顺手，且无模型接入限制。代价是客户端从零写。

### pi 的正确用法
**不作为内核，但强烈建议借鉴/移植 `packages/ai`**。若 codex 的 Responses API 限制成为阻塞，pi 的多 provider 抽象层正是现成解药——这可能是最终的组合拳：**codex 内核 + pi 的 provider 抽象思路**。
